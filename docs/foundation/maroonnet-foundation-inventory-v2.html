Part One

The Three Pillars

The platform (radios, command post application, storage) and the three analytical components that sit on it. This is the current focus and the subject of Tuesday's discussion.

1Where the design stands

MaroonNet is a mesh-networked location tracking and planning tool for search and rescue teams working where there is no cell service. Scope: location management, tracking, and logging. The system has four structural layers.

LayerContentsWhere covered
Radio and meshMeshtastic LoRa nodes on searchers, a gateway node at the command post, mesh routing§2
Command post applicationBrowser map, live positions, database, timelapse and coverage replay§3, §4
Analytical components (the three pillars)Sector Probability, Mesh Coverage Data, Mission Pre-Planning§5, §6, §7
Growth objectivesField User Sync, Drone Extension, Scrubbed ServerPart Two, §13 to §16

1.1The core loop

  1. Searchers carry Meshtastic LoRa radios that report GPS position and timestamp over the mesh.
  2. A gateway radio at the command post receives the mesh traffic and feeds a laptop.
  3. A browser map on that laptop shows the team lead live searcher positions over the search area.
  4. Everything received is written to a database.
  5. The three pillars compute on top of that data: where the person probably is, where the radios will and will not reach, and what plan gets teams out fastest.
  6. After the search, the database is replayed as a timelapse and coverage map for the after-action report, showing what was searched and what was missed.

1.2The three pillars in one line each

PillarDefinitionDepends on
Sector Probability (§5)The probability that the missing person is in sector X, from past search instances, geographic data, and current conditionsSector definitions, external historical and geographic data
Mesh Coverage Data (§6)The effective range from one radio hop to the next, from terrain and foliage, rendered as an overlay of where teams stay connectedNode positions (§2), elevation and land-cover data
Mission Pre-Planning (§7)Routes and sectors laid out before teams leave the command post, attacking the highest-probability ground first and knowing where contact will dropThe outputs of §5 and §6

Sector Probability and Mission Pre-Planning pair as the planning side; Mesh Coverage Data serves both planning and the live map. All three draw on the same geographic, topographic, and environmental data, which is why the data layer (§3.1, §5.2, §6.2) is a shared foundation rather than three separate downloads.

1.3The three growth objectives in one line each

Field User Sync (§13): every searcher's phone shows the other teams, the covered ground, and their own sector. Drone Extension (§14): a mesh radio a few hundred feet up to reach over ridges. Scrubbed Server (§15): after a mission, strip the personal data and keep the coverage layers so the next search in that area starts from history. None of the three is required for the pillars to work; each one is described in Part Two at the depth needed to decide whether and when to take it on.

1.4Framing decisions the team can design against

  • Not region-specific. Colorado is where we build and test because we are here and the terrain is hard. The system should serve a missing-person case in a city or in Nebraska farmland just as well. Every terrain and land-cover input in this document is a national or global dataset.
  • Not an extension of an existing product. CalTopo, COTAK, and the Meshtastic ecosystem each solve part of the problem (§8). MaroonNet uses their open-source components where they exist and builds its own open-source program with capabilities they lack. Reading and writing their file formats is still worth doing because it is cheap and it is how a team adopts a new tool without abandoning its records.
  • Ship one thing that works before starting the next. Rank the pillars, build and validate one until it is usable, then move to the next. The live map with sector coverage is the first demonstrable piece; the probability model is the piece that makes the pitch different.
  • Lower cost, easier to use, and generalizable. That is the differentiation against ATAK's learning curve and against subscription trackers. It is a design constraint on every piece below: no command line for the operator, one install, stock radios.

2Radio and mesh layer

Each searcher's node reports position and time over the mesh; the gateway node at the command post collects them. The radio is a collection sensor for time and location. It is not the storage or analysis point; those live on the laptop (§3, §4).

2.6The airtime ceiling

The default LongFast preset moves about 1 kbit/s. A 50-byte position packet occupies roughly 0.64 seconds of air, and every node within range rebroadcasts it. Ten nodes sending positions every 60 seconds, each rebroadcast twice, use about 19 minutes of airtime per hour, roughly 32% of the channel, already above the 25% polite threshold at which the firmware starts delaying sends. The same mesh on MediumFast uses about 9%. This answers the design question "how many nodes can share the mesh before reporting slows down": it depends on preset and interval, and the answer should be shown on the dashboard live (§9, airtime model). Preset and interval choices are engineering decisions, not defaults.

Open items to close with hardware in hand: whether the Heltec V4 GPS acquires reliably after flashing (a quirk has been reported); whether a gateway on the Python API needs its own GPS lock to relay others (CalTopo's serial mode does; expected not); and real-world range in Front Range terrain with stock versus upgraded antennas.

3.2Offline maps

An online map API (Google Maps, Mapbox, MapTiler) is exactly what cannot be used at a trailhead. Offline means the tiles are on disk before the mission. Planetiler turns an OpenStreetMap extract into vector tiles for a whole state in one run, a few gigabytes for Colorado at zoom 10–16. Vector tiles render at any zoom from one dataset, which is the reason to prefer MapLibre over a raster-first library. Add USGS 3DEP contours as a second tile layer so the map reads like the topo maps SAR people already use. Because OpenStreetMap, 3DEP, and NLCD cover the whole country, the same pipeline produces tiles for any state; nothing in the map layer is Colorado-specific.

What must be on the laptop ahead of time: the vector tile file for the region, the contour tiles, and, for the pillars, the DEM and land-cover rasters clipped to the working area. The application should let the operator pick a region at first run and download it while connected.

3.4Already glued versus must be built

Already glued: the Python library calls back into the daemon with a dictionary per packet; FastAPI talks to the browser over standard HTTP and WebSocket; MapLibre reads MBTiles or PMTiles from a static route; Shapely emits GeoJSON natively.

Must be built: the daemon; the schema (§4); the WebSocket message contract; every overlay (coverage grid, per-sector coverage numbers, mesh-coverage raster, probability surface, planned routes); the "node went quiet" alert logic; import and export mappers (§9); the provisioning UI. Four people building these in parallel without a written interface contract is the classic capstone failure, so the schema and message set get written before parallel work starts.

3.5Coverage and replay

The design doc asks how "coverage" is defined for the coverage map: the track alone, or the track plus a width on either side. The answer from search theory is the second: coverage is the track length times an effective sweep width (how far to each side a searcher of a given type reliably detects the subject in that terrain), divided by the sector area. Sweep width is a per-team-type, per-terrain input the incident commander can edit; the numbers themselves must come from practitioners (§12). Replay needs only the append-only history (§4.2): read the database at time T and redraw.

4Live mission storage

4.1One file per mission

Not a cloud database. The application's value is that it works at a trailhead with no signal, so anything requiring a network on the live path is a liability. The right shape is one SQLite file per mission on the command post laptop. Long-term, cross-mission storage is a different system with different rules and is covered under the Scrubbed Server (§15).

Geometry work (track-in-polygon intersection, buffering a track by sweep width, rasterizing coverage) runs in Python with Shapely and numpy, so the database itself does not need to be spatial. Consider making the mission file a GeoPackage (.gpkg): a SQLite file with a standardized schema for feature tables and rasters. It costs nothing because we are already in SQLite, and QGIS, GDAL, and every geospatial tool open it directly, which gives the mission archive export for free. Our own tables sit alongside the standard ones.

4.2Two rules that cannot be retrofitted

  • Append-only history. Positions, telemetry, packets, sector assignments, and events are inserted, never updated in place. Current state is a query over history. Replay is then just a read of the past; if state is overwritten, replay cannot be built later.
  • Two timestamps per row. The device's reported time and the command post's receive time. Field clocks drift; order by receive time, display device time.

4.3Retention and access

Store everything for the mission (replay needs it), keep the file on the command post laptop only, let the operator delete it, and never expose the local API on a network interface without authentication. Write this down as a decision before the first packet is stored. It is also the boundary the Scrubbed Server (§15.3) must respect.

5Pillar one: Sector Probability

Definition: the probability that the missing person will be found in sector X. Output: a probability per sector, giving the command post a ranked picture of where to send teams first. This is the piece that makes the pitch different, and it has one roadblock the team has not yet hit: the historical data.

5.1The science that already exists

Bayesian search theory is about eighty years old and well validated; the team should not claim to invent new search math. Current field practice is outdated in a specific way: probabilities are estimated by hand from published tables, and the results are typed into a mapping tool as sector overlays. There is no automated pipeline. The defensible novelty is to compute the probability surface directly from terrain, land cover, historical statistics, and current conditions, keep it as a live grid-level posterior that updates as searchers cover ground, and hand it to the planner (§7) automatically.

Every current-conditions feed requires internet at planning time. That is acceptable: planning happens before deployment, often at the station, and conditions are cached into the mission file (§4) so the offline map still shows them.

5.3The model to build first

A model that trains on incident data is not feasible in the capstone timeline because the training data is not available. A model that implements the published ring and watershed models from ISRID's published tables on open terrain data, then layers current conditions on top, is feasible, defensible, and already validated in the literature: on the MapScore metric, where a random map scores 0 and a perfect map 1, the ring model alone scores about 0.78 and the ring-plus-watershed combination about 0.81. That is the version to design first. The learning version becomes possible once the Scrubbed Server and the consent process exist (§15), which is after EXPO. The team's comfort with ML coursework is not wasted; it is what makes the second version credible, and it applies now to the evaluation harness (§5.5).

Inputs to the first version, concretely: subject category (from the initial call), initial planning point, elevation and slope, land cover, trail and road network, watershed boundaries, and any active hazard polygons. Output: a probability raster over the working area, then summed per sector.

5.4Sector definitions

The design doc asks how the search area is divided in the first place. Three sources, all of which the application should accept, because the probability surface is a raster and can be summed over any polygon:

  • Drawn by the incident commander on the map (minimal polygon tool).
  • Imported from another tool as GeoJSON or KML (§9).
  • Generated: the planner (§7.3) proposes sectors from the probability surface, terrain breaks, and trails; the commander edits them.

Whether the probability updates during the search: yes. As coverage accumulates in a sector (§3.5), the posterior for that sector falls by the fraction searched, and remaining probability re-ranks the open sectors. This is the "live grid-level posterior" from the September 3 discussion, and it is the same coverage math the live map already computes.

5.5Validation

The design doc asks how the team would know the probabilities are any good. Three tiers: sanity checks (probability sums to one, hazards zero out blocked cells, the surface moves the right way when inputs change); MapScore-style scoring against any historical cases a partner team shares, which is the standard the literature uses; and a planted-subject exercise where the team places a "subject" according to the published statistics and measures where the model ranked that sector. The first tier is free, the second needs one practitioner relationship, and the third is a day outdoors.

6Pillar two: Mesh Coverage Data

Definition: the effective range from one radio hop to the next, based on terrain and foliage. Output: a coverage overlay showing where teams stay connected and where the mesh drops out. This is the best-understood piece in the project because the inputs are free and the math is closed-form until full propagation models.

6.2From terrain between two points to "can they hear each other"

The algorithm, in the order it is built:

  1. Sample the DEM over the working area into a grid (30 m, or 10 m where available).
  2. For each transmitter (the gateway, any relay, or a candidate site) and each grid cell, sample the terrain profile along the straight line between them and test line-of-sight, adding antenna heights at both ends. A handheld is about 1.5 m; a gateway on a mast 2–6 m; a drone relay is simply a large antenna height (§14.1).
  3. Compute first-Fresnel-zone clearance along the profile. Sixty percent clearance is "clear"; partial clearance is "marginal."
  4. Compute the link budget: transmit power plus antenna gains, minus free-space path loss at 915 MHz, minus a foliage penalty per vegetated meter of path (published dB-per-meter figures for 900 MHz), minus a diffraction estimate for shadowed cells. Compare with the receiver sensitivity of the preset in use.
  5. Classify each cell as covered, marginal, or shadow for each transmitter; union across transmitters for the mesh overlay.

The design doc asks whether the overlay is computed before the search for planned node positions, live as nodes move, or both. Both, from the same code: pre-planning runs it for candidate relay sites and expected team routes (§7.2); the live map re-runs it for the current node positions. It is a numpy loop over data already loaded, roughly 40,000 cells by 200 profile samples for a 30-square-mile area, and it runs in seconds.

6.4Accuracy required

The overlay is a planning aid, not ground truth. It needs to be right often enough that an incident commander trusts "you will lose contact past that ridge" and plans a voice check-in. A reasonable target is that predicted class (covered, marginal, shadow) agrees with observed reception at least three times in four, with disagreements explainable.

6.5Validation

Formal published validation of LoRa range prediction against measured data is thin, so we validate it ourselves. During every outdoor test, log received signal strength and signal-to-noise ratio at the gateway for every position packet (§2.3) and compare against the predicted class for that cell. That log becomes the validation dataset, and nobody else has one for SAR terrain. Also compare our overlay against the Meshtastic Site Planner's output for the same gateway site and note the differences.

7Pillar three: Mission Pre-Planning

Definition: plan routes and sectors for the most efficient search before teams leave the command post. Inputs: the probability surface (§5) and the coverage overlay (§6). Output: where teams go, in what order, and where they will lose radio contact, so teams get out faster with a clear path set ahead of them. No existing tool automates this step (§8); it is where the pillars become a product.

7.1What "most efficient" means

The design doc asks whether efficient means highest-probability first, shortest travel, staying in mesh coverage, or a weighted mix. It is a weighted mix, and the weights should be visible and adjustable by the commander rather than hidden in code. The standard objective from search theory is to maximize probability of success per unit of effort: send each team where remaining probability divided by the time it costs to search there is highest. The terms in that ratio are:

  • Remaining probability in the sector (§5.4).
  • Time to search it: sector area divided by the team's sweep width and pace, adjusted for slope and land cover.
  • Time to reach it: travel from the command post or trailhead along trails and roads (a shortest-path over the OpenStreetMap network), adjusted for slope.
  • Contact risk: fraction of the sector and the approach in predicted shadow (§6.2). This does not forbid the sector; it schedules a check-in or a relay.
  • Hazard: sectors intersecting an active hazard polygon (§5.2) are excluded or deferred.

7.2Generated versus drawn

Generate a ranked plan; let the commander edit everything. The first version can be almost entirely ranking plus overlays: here are the sectors in priority order, here is the approach for each, here is where contact drops, here are the three relay sites that would fix it. Route generation inside a sector (parallel sweep lines at the sweep width spacing) is a small addition once the ranking exists. Anything more automated than that should wait for practitioner feedback; incident commanders will not accept a plan they cannot see the reasoning for.

7.3Sector generation

When no sectors are imported or drawn, the planner can propose them: split the working area along ridgelines, drainages, trails, and roads (all present in 3DEP and OpenStreetMap), size them to what one team searches in one operational period, and label them. This is the "generated" option in §5.4 and it is optional in the first version.

The claim is that teams get out faster. Measure it directly: time from "sectors defined" to "first team dispatched" with and without the tool, on the same scenario, in a table-top exercise with a practitioner if possible and with the team itself as the fallback. Also record how often the commander overrides the generated ranking and why; that is the feedback the model needs.

Part Two

The Three Growth Objectives

Not required for the pillars to work. Each is described at the depth needed to decide whether it is worth it, what it would take, and what in Part One it depends on.

13Field User Sync

Definition: live updates to field users of all location data for better in-field mapping. Every searcher sees the other teams, the covered ground, and their own sector boundaries in real time: fewer duplicated sweeps, fewer teams crossing into each other's areas, faster reaction when a neighboring team finds something.

13.1What the mesh already does

The physics answer is simpler than the design doc assumes. Because the mesh floods every broadcast (§2.1), every node already hears every other node's position and stores it. A phone paired to a node over Bluetooth reads that node's database and draws it. There is no server, no upload, no download, and no round trip through the command post. Field-to-field awareness of positions therefore exists today with stock firmware and the stock app; the gap is everything richer than a dot and a name.

DirectionPayloadMechanismWhere it shows up today

Command post to fieldText messageChannel broadcast, or encrypted direct message with acknowledgementStock app messages tab
Command post to fieldWaypoint (one point with name, icon, expiry)Waypoint packetStock app map
Command post to fieldConfig changes (intervals, role, channel)Admin message using a key stored on the nodeReboots the node

13.2What does not flow without a custom app

PayloadWhy not
Sector polygonsNo polygon primitive; 233-byte cap (§2.4); stock apps ignore custom message types
Assignments, coverage overlays, probability surfaces, planned routesSame
Anything larger than a text messageAirtime (§2.6). A 2 KB polygon on LongFast is roughly 20 seconds of channel time per hop.

Design consequence: the command post can already tell a field team "go to this point" and "your sector is B; the boundary is on the paper map" (§7.4). Drawing the boundary on their phone requires our own app and a compact encoding (simplified polygon, or a sector ID that the phone resolves against a pre-loaded plan).

13.4What a custom app would add

Sector polygons and assignment labels on the searcher's phone; "you are outside your sector" warnings; live coverage feedback to the searcher; the planned route from §7; richer command-to-field acknowledgement than a text. All of it needs a custom message type on the mesh plus airtime budgeting.

13.5Phone-specific roadblocks

iOS restricts Bluetooth in the background, so positions arrive only while the app is foregrounded or holds location permission. BLE plus screen drains batteries. Every searcher needs both a radio and a phone. App Store review runs weeks against a capstone calendar. Two platforms' worth of bug reports from volunteers. The stock app already absorbs all of this.

13.6Dependencies and recommendation

Depends on: the mesh having airtime to send data outward (§2.6), the plan existing in a compact form (§7), and a sector encoding small enough for the payload cap. Independent of the probability model. Recommendation: split it in two. Field-to-field awareness is done; use the stock app and demonstrate it. Command-to-field sectors get a named design (custom message type plus a Kotlin Multiplatform app) as the next version, so the pitch says exactly what comes next rather than promising it now.

14Drone Extension

Definition: a drone carrying an extra mesh radio to extend range. A radio a few hundred feet up sees over ridges that ground radios cannot; paired with the coverage model, planners know how much more of the search area an airborne relay brings into contact.

14.1The coverage algorithm already handles it

An elevated node is an antenna-height parameter in step 2 of §6.2. A relay at 120 m above ground is the same line-of-sight and link-budget calculation with a taller transmitter, and the relay-placement pass in §6.3 can evaluate candidate hover points exactly as it evaluates ridge sites. This means the modeling half of the drone idea costs almost nothing once §6 exists: show the coverage gain of a relay at a given hover point and altitude, and let the commander decide whether it is worth flying.

14.2Flight, payload, and airspace

ConstraintReality
PayloadA field node with battery and antenna is 100–200 g; well within a consumer or prosumer quadcopter's margin
Flight time20–40 minutes per battery for most consumer platforms; a relay that must stay up needs a battery-swap cycle (fly out, hover, return, swap) and a dedicated operator at the command post, as discussed on September 3
AirspaceNon-recreational flight falls under FAA Part 107 (a certified remote pilot, 400 ft ceiling above ground, visual line of sight). Some SAR agencies fly under public-aircraft rules instead. Wilderness areas and national parks restrict or prohibit drones.
Weather and terrainWind at ridge height, cold-weather battery loss, and altitude density all cut flight time in the terrain where a relay is most useful
Drone data accessDJI's mobile SDK is closed and restricted; open flight stacks (ArduPilot, PX4 over MAVLink) allow full telemetry but mean building or buying a non-DJI airframe. For a relay, none of this matters: the node on the drone talks to the mesh directly and the drone is just a lift.

14.3Modeling exercise or hardware exercise

Modeling first, and possibly only. The coverage gain of an airborne relay is demonstrable on the map without a drone, and it is the same demonstration a mast relay gets (§2.5). A mast is cheaper, stays up all day, needs no pilot, and is legal everywhere; it is the ground-based form of the same idea and the one to build if the team wants a physical relay at all. A drone flight is a compelling demo if a certified pilot and a suitable site are available, but it should not shape the core system.

15Scrubbed Server

Definition: since location data is already collected for the probability model, a server-side component scrubs the data after the algorithms have used it and stores the resulting mapping in layers. Layers for pre-planning: future searches in the same area start from real history. Layers for late teams: arriving teams load current coverage and go straight to unsearched ground. A stored record for after-action review, training, and old cases.

15.1Separate from the live database

The design doc asks whether this lives on the command post laptop or is synced somewhere afterward. It is a separate system, synced afterward, for four reasons.

  1. Different lifecycle. The live file (§4) is created at mission start, read for replay, then archived. The server accumulates across missions and teams.
  2. Different access control. The live file holds named people's exact positions. The server must not.
  3. Different connectivity. The live file is offline by design; the server is online by design.
  4. Different consent. A team recording its own exercise is one thing. Contributing to a cross-agency database is an opt-in act with an IRB and consent-form trail.

15.3What scrubbing removes and what it keeps

RemovedKept
Node IDs, device names, operator names, team names, message textTeam type (foot, dog, vehicle) and sweep width used
Exact timestamps (coarsen to the operational period)Date, season, weather and hazard state at the time
Individual tracks (replace with the coverage raster they produced)Coverage per cell per period; sectors with their coverage and probability numbers

The last row is what makes the server feed back into the probability model (§5.2, last row): the anonymized find location relative to the initial planning point, by subject category, terrain, and conditions, is precisely the statistic ISRID holds and the team cannot otherwise obtain. Every contributing team's outcomes make the next team's model better.

15.4Ownership, access, and dependencies

The contributing agency owns its data and can withdraw it; the layers derived from many agencies' data are shared under the same open license as the software. Access to raw uploads is limited to the contributing agency; access to derived layers is open to any team running the software. Depends on: the live database and its schema (§4), the append-only history that makes an export complete, the IRB and consent process (§9), and internet at the station after the mission. Feeds: the probability model (§5) and the planner (§7) with real history instead of a blank map.
